## Comparison caveats

Use the frozen 69-recording public-human corpus and identical normalization, references, audio hashes and term scoring. It is a repeatedly inspected comparison set, not untouched final validation. Podcast speech is not a production noisy-call benchmark. No reference-derived hints or hotword prompts. Prefix probes measure fresh decode compute, not live capture-to-text latency. Run one candidate at a time on the GPU.

GigaAM frontend/decoding are intentionally on CPU and included in timing. Its official short-file API rejects audio longer than 25 seconds; the benchmark directly invokes the same encoder/head on whole recordings up to 59.4 seconds, so this adapter must be validated separately from claims about the stock transcribe API. Memory sampled from MPS counters every 20ms can miss short peaks and must not be presented as an exact MLX allocator peak.

## GigaAM reproducibility finding

Stock SDPA on torch 2.10.0/MPS was not reproducible: first pass 365 word edits, second 980, with only 19/69 identical transcripts. This disqualifies that execution path; do not report only the favorable run. The underlying cause is not yet isolated to a specific PyTorch kernel.

Setting `torch_sdpa_attn=False` on all Conformer attention layers selects the author's existing explicit matmul/softmax attention path. Two fresh-process full-corpus runs then matched 69/69 hypotheses, both with 365 edits, and matched the favorable initial SDPA transcripts. The benchmark defaults to explicit attention; `--use-sdpa` exists solely to reproduce the failing route. There are no changes to downloaded weights or source code.

Explicit-attention results: overall WER 10.57%; Russian 6.72%; mixed 16.83%; English 13.71%; exact Latin-term recall 2/60. Compute 15.59 and 13.52 seconds over 1370.47 seconds of audio. The MPS 20ms sample maxima were 1.28 GB allocated / 2.22 GB driver memory; RSS ~1.22 GB. These counters are not additive, and sampled maxima are not exact peaks.

An example failure is `performance review` rendered with mixed-script letters, and `observability` rendered phonetically in Cyrillic. This is relevant to preserving technical terms, even when a human could understand the intended term.

## Voxtral runtime screen (not a full benchmark)

Voxtral int4 with delay 480ms processed the first ten files in 209.93 seconds for 195.53 seconds of audio (RTF 1.074). It used 5.94 GB peak MLX allocation and 3.15 GB total local model files. This is the installed community MLX implementation on the currently loaded M3 Pro, not a claim about all Voxtral implementations or devices. CPU/background load was not controlled and system swap was in use.

The first ten include nine Russian files and only one mixed file, with no English-only control. Therefore this screening cannot establish general RU/EN code-switch quality. It was a runtime stop decision after observing performance, not a pre-registered quality subset. The raw `voxtral.json` correctly remains `complete:false`; the result is never merged into the 69-file leaderboard. No full repeat or live-audio session was performed for Voxtral.

## Final recommendation for this Mac

- Russian-first compact recognizer: GigaAM Multilingual CTC is a promising new option (~883 MB weights). Use explicit attention in our MPS adapter; stock SDPA failed repeatability. Validate live segmentation and noisy calls before adding it as a product backend.
- Russian with English technical terms: retain Qwen3-ASR 1.7B as the best measured full-corpus candidate. GigaAM's Russian advantage does not carry over to term spelling.
- Voxtral int4: no demonstrated advantage here. Revisit only with an optimized runtime or controlled live-stream benchmark; don't replace the current backend based on its 480ms configuration label.
- Broader-language research: omniASR CTC 300M remains untested. SenseVoice Small, Moonshine Streaming and Fun-ASR-MLT-Nano do not satisfy the published Russian-language requirement.
